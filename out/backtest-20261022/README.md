**B 组结论：否定。加入其他项目的历史 issue 后，模型提出能抓到真实 bug 的测试，比例没有提高。** 49 道有效题中，A 组（只读代码）和 B 组（读代码 + 检索历史）都是 15 道命中，提升 0 个百分点，95% 置信区间 [−8.2, +8.2]，McNemar p = 1.0。B 组的输入 token 是 A 组的 2.06 倍。按 [评测设计](../../docs/evaluation.md) 里跑之前写定的条件，Issue Lens 不再作为测试生成增强工具继续投入，语料保留为数据集。

## 判分可靠性

我复核了 8 道题：4 道分歧题，以及 2 道双命中和 2 道双未中。8 道里判分都和我自己的判断一致。复核者也是模型，不是人工，所以这只说明判分没有明显偏差，不能当成人工一致率。

## 这个结论的边界

- **只测了一种用法**：模型自己出检索词，用 FTS 关键词检索，原始 issue 直接喂给模型。语义检索、人工整理的故障模式（例如 `out/quality-20261021/lessons_*.md`）都没有测过。
- **只用了一个模型**：Codex CLI `gpt-6.1-sol`。题目限定在 2026-04-01 之后，但模型可能已经见过这些项目的代码或同类 bug。
- **提示偏强**：模型拿到的是被修复文件中改动位置前后各 80 行，等于知道 bug 在哪。这样两组的命中率都偏高，可能把历史能补上的那部分空间挤掉了。
- **判分不是执行**：判的是“按这条测试执行会不会失败”，没有真的执行。
- **1 道题失败**：yt-dlp#16729 两次都返回非法 JSON，按失败记录，不计入 49 道。另有 6 道选题时网络失败、114 道不符合条件（没有合并的修复 PR、改动文件太多、只改了测试或样式），都已记在选题日志里。

## 试跑

正式运行前有两轮试跑，共 6 道题。试跑后改了三处：只给改动附近的代码，排除纯样式修复，主指标改为“命中或指出同一故障机制”。这 6 道题不在正式题集里。

## C 组：整理过的故障模式（同一题集，同一判分）

**结论：仍然否定。** C 组不给原始 issue，改给 `out/quality-20261021/lessons_*.md` 里的 21 条故障模式，每条都有机制说明和测试思路。这些模式由 reviewer agent 从抽样 issue 归纳而来，没有经过人工校对。泄漏规则和 B 组相同：如果模式引用了同一仓库、并且不早于题目的 issue，这道题就不给这条模式；被保留的模式至少要引用一条早于题目的 issue。最终每道题拿到 20–21 条。

| | A：只读代码 | C：代码 + 故障模式 |
|---|---:|---:|
| 主指标 | 15 / 49 | 14 / 49 |
| 严格命中 | 11 / 49 | 12 / 49 |
| 只有这一组命中 | 5 | 4 |
| 提升（95% CI） | | −2.0 个百分点（−14.3 ~ +10.2），McNemar p = 1.0 |
| distributed 子集 | 6 / 15 | 4 / 15 |
| 输入 token | 1,259,498 | 1,620,199（1.29 倍） |

C 对 B：14 比 15，−2.0 个百分点（−10.2 ~ +6.1）。

- **模式被大量引用，但没有带来帮助**：245 条测试里有 204 条（83%）引用了模式，远高于 B 组引用历史的 11%。不过引用很集中：一共 247 次引用里，consensus-7（“只在某种模式、配置分支或输入形状下才走到的缺陷代码路径”）占了 91 次。这条几乎能套到任何代码上，引用它更像是贴标签，而不是借鉴具体机制。
- **C 独有的 4 次命中都引用了模式**，其中 3 次引用的就是 consensus-7（envoy#45491、react-router#15255、ollama#15260）。从判分理由看，命中靠的是读代码时发现的具体问题，和模式里写的机制关系不大。
- **在模式本该最有用的 distributed 题上反而更差**（4 比 6）。A 独有命中的 nomad#28538 和 tikv#19891，C 组的 5 条测试都转向了模式里的通用场景，例如锁释放、删除重建、流程中途失败，错过了代码里真实的部署状态和序列号问题。

## D 组：同一仓库自己更早的 issue（同一题集，同一判分）

**结论：否定（提升 < 5 个百分点，置信区间包含 0）。** D 组只给同一仓库里创建并关闭都早于这个 bug 的 issue（分层为 core/usable）。沿用 B 组的检索词时，49 道里有 34 道一条也查不到，因为 B 的检索词刻意不用项目内名称。所以 D 组单独生成检索词，允许使用本项目的模块名、函数名和配置名；仍查不到时，用改动文件的文件名补充。题集、判分和放弃条件不变。最终每题检索到的同仓库历史中位数是 3 条，3 道题一条也没有。

| | A：只读代码 | D：代码 + 本仓库历史 |
|---|---:|---:|
| 主指标 | 15 / 49 | 17 / 49 |
| 严格命中 | 11 / 49 | 11 / 49 |
| 只有这一组命中 | 2 | 4 |
| 提升（95% CI） | | +4.1 个百分点（−6.1 ~ +14.3），McNemar p = 0.69 |
| 有本仓库历史的 46 题 | 14 | 16（+4.3，−6.5 ~ +15.2） |
| 输入 token | 1,259,498 | 2,548,185（2.02 倍） |

- **提升解释不了是历史带来的**：D 独有的 4 次命中中只有 1 次引用了本仓库历史（vscode#334144）。另外 3 道是 ollama#15260、envoy#45491、react-router#15255：ollama 那道 B、C、D 都命中，envoy 和 react-router 那两道 C、D 都命中，只有 A 没中。这几道题换一种提示就可能碰巧命中，差异更像生成的随机性，而不是知识的作用。
- **模型同样很少用这些历史**：245 条测试里只有 45 条（18%）引用了本仓库历史。

## 总的判断

原始历史（B）、整理过的模式（C）、本仓库历史（D）三种用法都没有让模型写出明显更能抓到 bug 的测试。B 是“模型基本不用”；C 是“模型用了，但注意力被从代码本身分散开”；D 的小幅差异集中在几道换个提示就可能命中的题上。在这套题和这个模型上，**历史 bug 知识没有可测的增益**，Issue Lens 作为测试生成增强工具的设想不成立。

还没覆盖到的情况：可执行判分、其他模型、不提示 bug 位置的整库审查。在整库审查里，模型不知道该看哪里，历史知识也许能帮它挑重点。这是与这次不同的问题，需要另外出题。
